# DSH AutoInstall

Менеджер установки [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) (`dsh`) с доступом к веб-интерфейсу из локальной сети (LAN).

Репозиторий содержит один сценарий — [`dsh.sh`](./dsh.sh). Текущая версия сценария — **3.2** («показать URL с токеном», токен не сжигается при проверке).

Начиная с версии 3.x сценарий работает как менеджер полного цикла: установка, обновление с бэкапом, полное удаление, восстановление из бэкапа и вход по токену — плюс интерактивное меню. LAN-доступ обеспечивается плагином `dsh-web-lan-access`; внутренности пакета `dsh` больше **не** патчатся.

> **Важно:** адаптер доступа из LAN специально ослабляет loopback-проверки для доверенной сети. У `dsh` нет встроенной пользовательской авторизации, поэтому любой, кто получил доступ к порту, сможет менять настройки, credentials и модель. Не публикуйте порт напрямую в Интернет и не настраивайте проброс на WAN.

## Возможности

Основные сценарии (режимы запуска):

| Режим | Что делает |
| --- | --- |
| `./dsh.sh` | Интерактивное меню (установка, обновление, удаление, восстановление, показ токена). |
| `./dsh.sh install` | Устанавливает последнюю версию `dsh` «с нуля»: Node.js/pnpm, глобальный пакет, плагин LAN-доступа, systemd-сервис. |
| `./dsh.sh update` | Делает бэкап `~/.dsh` и `~/dsh-workspace`, затем выполняет установку последней версии. |
| `./dsh.sh uninstall` | Полностью удаляет `dsh`: сервисы, пакет, бинарники, процессы. Данные пользователя удаляются по отдельному подтверждению (с опциональным бэкапом). |
| `./dsh.sh restore` | Показывает список бэкапов и восстанавливает выбранный. |
| `./dsh.sh token` (синоним `url`) | Показывает URL для входа со свежим токеном из логов сервиса. |
| `./dsh.sh --help` | Краткая справка по аргументам. |

Интерактивное меню:

```text
  1) 🗑  Удалить DSH (полное удаление)
  2) 📦 Установить последнюю версию DSH
  3) 🔄 Обновить DSH (с бэкапом)
  4) ♻️  Восстановить из Backup
  5) 🔑 Показать URL для входа (с токеном)
  0) 🚪 Выход
```

В шапке меню выводятся пользователь, `HOME`, порт, каталог бэкапов, путь к логу, а также состояние `dsh` и systemd-сервиса.

### Что делает установка (пункты 1–9)

1. Определяет LAN IP (`hostname -I`, исключая loopback и link-local).
2. Добавляет ключи `github.com` в `~/.ssh/known_hosts` через `ssh-keyscan`.
3. Проверяет Node.js: поддерживаются `^22.19 || >=24`. Если версия отсутствует или не подходит, ставится Node.js 24 из NodeSource через `apt-get`.
4. Проверяет `pnpm` и при необходимости устанавливает его глобально через npm.
5. Устанавливает глобально `@deepseek-ai/dsh@latest` (`npm install -g`), затем выводит версию, путь до бинарника и предупреждение, если версия старше `0.1.5`.
6. Устанавливает плагин `dsh-web-lan-access` из npm, а при ошибке — из GitHub (`github:AcidGr/dsh-web-lan-access`); результат проверяется через `dsh plugin --profile web list`.
7. Исправляет владельца каталогов `~/.dsh` и `~/dsh-workspace`, если они существуют.
8. Останавливает и отключает старые сервисы `dsh`, `caddy-proxy`, `caddy-https`, удаляет их unit-файлы и освобождает порт.
9. Создаёт и запускает `dsh.service` (`ExecStart=<dsh> web --port <порт> --no-open`, автозапуск включён). Если активного systemd нет — запускает процесс через `nohup` с логом `~/dsh.log`.

В конце выполняется проверка результата: HTTP-код веб-интерфейса, наличие токена в логах (токен при этом не сжигается), доступность `settings.describe` с LAN-хостом, блокировка внешних Host (`403`) и активность плагина.

### Обновление

`update` отличается от `install` только предварительным бэкапом: если существуют `~/.dsh` или `~/dsh-workspace`, создаётся архив `before_update`, после чего выполняется тот же сценарий установки последней версии. Перед пересозданием сервиса старый unit-файл `dsh.service` удаляется.

### Вход по токену (пункт меню 5)

`dsh` печатает в лог одноразовую ссылку вида `http://<host>:<port>/?token=...`. Пункт **5** достаёт последний токен из журнала сервиса (`journalctl -u dsh`) или из `~/dsh.log` и показывает готовые ссылки — для локальной сети и для самого сервера:

```text
http://<LAN-IP>:3080/?token=<TOKEN>
http://127.0.0.1:3080/?token=<TOKEN>
```

Токен **одноразовый**: после первого успешного входа он сгорает, а браузер получает cookie примерно на 30 дней, поэтому дальше интерфейс можно открывать просто по `http://<LAN-IP>:3080/`. Проверки в сценарии токен не используют, поэтому он не «сжигается» до того, как вы им воспользуетесь.

Если токена в логах нет, сценарий предложит перезапустить сервис (`sudo systemctl restart dsh`), чтобы получить свежий токен, а в конце может перезапустить сервис ещё раз по отдельному подтверждению — например, если предыдущий токен уже был использован.

### Бэкапы

- Каталог по умолчанию — `~/dsh_backups` (переопределяется переменной `DSH_BACKUP_DIR`).
- В архив попадают только существующие каталоги: `~/.dsh` и `~/dsh-workspace`. Логи, ключи SSH и сам npm-пакет в бэкап не входят.
- Имя файла: `dsh_backup_<YYYYMMDD_HHMMSS>_<метка>.tar.gz`. Метки: `before_update`, `before_restore`, `before_uninstall`, `manual`.
- Если бэкапить нечего, сценарий предупреждает об этом и не создаёт пустой архив.

Восстановление (`restore` или пункт меню **4**):

1. Показывает список архивов с датой и размером, выбор — по номеру.
2. После подтверждения останавливает сервис и процессы, слушающие порт.
3. Создаёт страховочный бэкап текущего состояния (`before_restore`).
4. Удаляет `~/.dsh` и `~/dsh-workspace` и распаковывает выбранный архив в `$HOME`.
5. Возвращает владельца каталогов пользователю и запускает сервис, если unit-файл существует, ожидая открытия порта.

Существующие архивы при восстановлении и удалении не удаляются.

## Требования

Целевая среда — Linux на базе Debian/Ubuntu с:

- Bash и правами `sudo`;
- доступом в Интернет к NodeSource, npm и GitHub;
- `curl`, `hostname`, `ssh-keyscan`, `ss` (или `netstat`), `tar`, `find`, `getent`, `readlink`, `grep -P`;
- работающим systemd — рекомендуется для автозапуска, но сценарий умеет работать и без него;
- Node.js `^22.19 || >=24` — при необходимости устанавливается автоматически.

Сценарий можно запускать как от обычного пользователя, так и из-под `sudo`. При запуске через `sudo` сценарий определяет исходного пользователя (`SUDO_USER`), подменяет `HOME`/`USER` на его значения и создаёт сервис от его имени. Если запустить от root без `SUDO_USER`, все файлы и сервис будут привязаны к `root`.

## Быстрый старт

```bash
git clone https://github.com/UglyRacoon/DSH_AutoInstall.git
cd DSH_AutoInstall
chmod +x dsh.sh
./dsh.sh
```

Выберите пункт **2** для установки. По завершении в выводе будет адрес входа вида:

```text
http://<LAN-IP>:3080/?token=<TOKEN>
```

Откройте его с компьютера в той же сети (ссылку с `127.0.0.1` используйте для входа на самом сервере) и выполните:

1. `Settings` → `Models`.
2. Укажите API-ключ DeepSeek, если он не был передан заранее.
3. Выберите модель и сохраните настройки.
4. Выберите рабочую папку (`Workspace`), иначе composer может быть недоступен.

Если токен уже использован или потерялся — пункт меню **5** покажет ссылку снова или получит свежую после перезапуска сервиса.

### Перед запуском

Сценарий имеет потенциально разрушительные действия:

- останавливает и отключает сервисы `dsh`, `caddy-proxy`, `caddy-https`;
- удаляет `/etc/systemd/system/dsh.service`, `caddy-proxy.service`, `caddy-https.service`;
- завершает процессы, слушающие выбранный порт;
- при удалении и восстановлении безвозвратно перезаписывает или удаляет `~/.dsh`, `~/dsh-workspace` и `~/dsh.log` (в восстановлении и удалении есть страховочный/опциональный бэкап).

Если на сервере уже используются dsh, Caddy или порт `3080`, заранее сохраните их конфигурацию и проверьте содержимое сценария.

## Переменные окружения

Переменные читаются при запуске сценария:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DSH_PORT` | `3080` | Порт веб-интерфейса (используется в `dsh web --port`, в ссылках и в проверках). |
| `DSH_BACKUP_DIR` | `$HOME/dsh_backups` | Каталог для архивов бэкапа. |
| `DSH_SKIP_PLUGIN_INSTALL` | `0` | При значении `1` плагин `dsh-web-lan-access` не устанавливается. LAN-доступ работать не будет. |
| `DEEPSEEK_API_KEY` | не задана | Если задана, добавляется в окружение systemd-сервиса `dsh`. |

Пример запуска на другом порту:

```bash
export DSH_PORT=8080
./dsh.sh
```

Если вы запускаете сам сценарий через `sudo`, используйте `sudo -E`, чтобы передать переменные окружения:

```bash
sudo -E ./dsh.sh
```

### API-ключ

Ключ можно передать сервису заранее:

```bash
export DEEPSEEK_API_KEY='sk-...'
./dsh.sh install
```

При запуске через `sudo` используйте `sudo -E`, иначе переменная не дойдёт до сценария. Учтите, что ключ записывается в `/etc/systemd/system/dsh.service` в открытом виде — ограничьте доступ к unit-файлу и не передавайте ключ в командной строке на общей машине. Если ключ не задан, его можно ввести позже в `Settings` → `Models`.

## Что изменяется на диске

| Путь | Назначение |
| --- | --- |
| `/etc/systemd/system/dsh.service` | Unit-файл сервиса (`dsh web --port <порт> --no-open`) и его автозапуск. |
| `~/dsh_YYYYMMDD_HHMMSS.log` | Основной лог запуска; путь выводится в заголовке меню и при ошибках. |
| `~/dsh.log` | Лог фонового запуска через `nohup`, если активный systemd не найден. |
| `~/dsh_backups/` | Архивы бэкапов (`dsh_backup_*_<метка>.tar.gz`). |
| `~/.dsh` | Данные и настройки `dsh` (создаются самим `dsh`, сценарий только меняет владельца). |
| `~/dsh-workspace` | Рабочая папка (создаётся самим `dsh`, сценарий только меняет владельца). |
| `~/.ssh/known_hosts` | Добавленная запись для `github.com`. |

Фактический домашний каталог зависит от пользователя, определённого сценарием (см. раздел «Требования»).

## Управление сервисом

На системах с работающим systemd:

```bash
sudo systemctl status dsh
sudo systemctl restart dsh
sudo systemctl stop dsh
sudo journalctl -u dsh -f
```

Проверка порта и веб-интерфейса:

```bash
ss -ltnp | grep ':3080'
curl -I http://127.0.0.1:3080/
```

`HTTP 401` на `/` означает, что сервис работает и требует токен, — это нормально до входа по ссылке из пункта меню **5**. Остановленный или «упавший» сервис перезапускается автоматически (`Restart=on-failure`, `RestartSec=10`).

Если systemd не активен, сценарий запускает `dsh` через `nohup`; автозапуск после перезагрузки в этом режиме не настраивается. Лог такого запуска — `~/dsh.log`.

## Firewall и безопасность

Firewall сценарий не меняет. Ограничьте порт только нужной подсетью, например для сети `192.168.0.0/16`:

```bash
sudo ufw allow from 192.168.0.0/16 to any port 3080 proto tcp
```

Адаптируйте подсеть и порт под свою сеть. Не используйте широкое правило вроде `allow 3080/tcp`, не настраивайте проброс порта на WAN и не считайте LAN-доступ заменой аутентификации или TLS.

Дополнительно учитывайте:

- вход в веб-интерфейс защищён только одноразовым токеном и cookie, которые выдаёт `dsh`;
- токен из журнала сервиса имеет смысл считать секретом: он даёт полный доступ к настройкам и credentials;
- плагин и глобальный пакет устанавливаются из внешних источников (npm, GitHub) и требуют сетевого доступа;
- скрипт добавляет результат `ssh-keyscan` в `known_hosts`; перед использованием в строгой модели безопасности проверьте отпечаток ключа GitHub самостоятельно;
- обновление `dsh` перезаписывает глобальный пакет: если вы использовали сторонние патчи из версий 2.x, они будут потеряны — в 3.x LAN-доступ обеспечивается плагином, а не патчами.

## Диагностика

### Веб не отвечает

```bash
sudo systemctl status dsh
sudo journalctl -u dsh --no-pager -n 100
ss -ltnp | grep ':3080'
```

Убедитесь, что `dsh` есть в `PATH` и порт не занят другим процессом. Сценарий при установке печатает HTTP-код проверки: `200`/`302`/`401` — норма, `000` — сервис не поднялся или таймаут ожидания порта (90 секунд).

### Не найден токен

1. Выполните `./dsh.sh token` (или пункт меню **5**) — сценарий предложит перезапустить сервис для свежего токена.
2. Вручную: `sudo systemctl restart dsh && sudo journalctl -u dsh -n 100 | grep -i token`.
3. Если сервис запущен без systemd, смотрите `~/dsh.log`.

### LAN возвращает `403` / «settings are unavailable in this browser»

1. Проверьте, что плагин активен: `dsh plugin --profile web list | grep lan-access`.
2. Если плагина нет — установите его: `dsh plugin --profile web add dsh-web-lan-access` (запасной источник — `github:AcidGr/dsh-web-lan-access`). Не задавайте `DSH_SKIP_PLUGIN_INSTALL=1`.
3. Открывайте интерфейс по `http://<LAN-IP>:<порт>`, а не по имени хоста, которое может разрешаться неоднозначно, и обновите страницу с очисткой кэша (`Ctrl+Shift+R`).
4. Помните, что внешние Host намеренно должны оставаться заблокированными (`403`) — сценарий проверяет это отдельно.

### Сервис не запускается после обновления

Проверьте статус и журнал, затем повторно выполните установку/обновление: сценарий заново создаст unit-файл и освободит порт.

```bash
sudo journalctl -u dsh --no-pager -n 100
./dsh.sh update
```

### Восстановление или удаление прошло не так, как ожидалось

- Все операции с пользовательскими данными создают страховочный бэкап (`before_restore`, `before_uninstall`) в каталоге `DSH_BACKUP_DIR`.
- Посмотрите список архивов пунктом меню **4** и восстановите нужный.
- Основной лог текущего запуска указан в шапке меню и в сообщении об ошибке.

## Повторный запуск и откат

- Повторный запуск `install`/`update` безопасен для данных: он переустанавливает пакет, плагин и unit-файл, не трогая `~/.dsh` и `~/dsh-workspace`.
- Для полного удаления используйте `./dsh.sh uninstall` (или пункт меню **1**) — сценарий сам предложит создать бэкап перед удалением пользовательских данных.
- Минимальная ручная остановка сервиса:

```bash
sudo systemctl disable --now dsh
sudo rm -f /etc/systemd/system/dsh.service
sudo systemctl daemon-reload
```

- Архивы бэкапов удаление не затрагивает: их можно хранить и переносить на другую машину вручную.

## Проверка репозитория

Сценарий не содержит отдельного набора автоматических тестов. Базовая проверка синтаксиса выполняется без запуска установки:

```bash
bash -n dsh.sh
```

Полезно также посмотреть справку и меню (без sudo, ничего не устанавливая):

```bash
./dsh.sh --help
./dsh.sh          # затем введите 0 для выхода
```

Полноценная проверка требует Linux-системы с `sudo`, Node.js/npm, доступом к сети и возможностью запустить `dsh`.
