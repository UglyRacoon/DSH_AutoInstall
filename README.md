# DSH AutoInstall

Автоматизатор установки и настройки [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) (`dsh`) с доступом к веб-интерфейсу из локальной сети (LAN).

Репозиторий содержит один установочный сценарий — [`dsh.sh`](./dsh.sh). На момент последнего обновления сценарий имеет версию **2.2**.

> **Важно:** сценарий открывает веб-интерфейс на всех сетевых интерфейсах (`0.0.0.0`) и специально ослабляет loopback-проверки для доверенной LAN. У `dsh` нет встроенной авторизации, поэтому любой пользователь, получивший доступ к порту, сможет менять настройки, credentials и модель. Не публикуйте этот порт напрямую в Интернет.

## Возможности

`dsh.sh` выполняет следующие действия:

1. Определяет пользователя, от имени которого должен работать сервис, и его домашний каталог.
2. Определяет первый найденный IPv4-адрес локальной сети.
3. Добавляет ключи `github.com` в `~/.ssh/known_hosts` для установки зависимостей из GitHub.
4. Проверяет Node.js. Поддерживаемыми считаются версии `22.19+` ветки 22 и `24+`; при отсутствии подходящей версии сценарий устанавливает Node.js 24 через NodeSource и `apt-get`.
5. Проверяет наличие `crypto.randomUUID` в Node.js.
6. Устанавливает глобально `pnpm` и пакет `@deepseek-ai/dsh`, если они отсутствуют.
7. Создаёт LAN-оверлей `~/.dsh/overlays/lan.yml` с адресом `0.0.0.0` и портом веб-интерфейса.
8. Исправляет владельца каталогов `~/.dsh` и `~/dsh-workspace`, если они существуют.
9. Останавливает старые systemd-сервисы `dsh`, `caddy-proxy` и `caddy-https`, удаляет их unit-файлы и освобождает выбранный порт.
10. Устанавливает плагин `dsh-web-lan-access` из npm, а при ошибке — из GitHub.
11. Патчит серверный и клиентский код `dsh-client-connection`, чтобы Settings/Models были доступны по LAN. Перед изменением создаются файлы с суффиксом `.dshbak`.
12. Создаёт и запускает `dsh.service` с автозапуском через systemd. Если systemd не работает, используется фоновый `nohup` без автозапуска.
13. Проверяет HTTP-ответ, LAN-доступ к `settings.describe`, блокировку внешнего Host, плагин и отдаваемый клиентский код.

Сценарий **не** настраивает firewall, HTTPS или аутентификацию и не выбирает модель автоматически.

## Требования

Целевая среда — Linux на базе Debian/Ubuntu с:

- Bash и правами `sudo`;
- доступом в Интернет к NodeSource, npm и GitHub;
- `apt-get` для автоматической установки Node.js;
- стандартными утилитами Linux, включая `curl`, `hostname`, `ssh-keyscan`, `ss`, `find`, `readlink`, `python3` или `perl`;
- работающим systemd — рекомендуется для автозапуска, но сценарий умеет работать без активного systemd.

Сценарий рассчитан на запуск от обычного пользователя с правами `sudo`. Запуск непосредственно от root возможен, но тогда рабочие файлы и сервис будут привязаны к root, что обычно нежелательно.

## Быстрый старт

```bash
git clone https://github.com/UglyRacoon/DSH_AutoInstall.git
cd DSH_AutoInstall
chmod +x dsh.sh
./dsh.sh
```

В процессе сценарий может запросить пароль `sudo`. По завершении в выводе будет адрес вида:

```text
http://<LAN-IP>:3080
```

Откройте его с компьютера в той же сети и выполните:

1. `Settings` → `Models`.
2. Укажите API-ключ DeepSeek, если он не был передан заранее.
3. Выберите модель и сохраните настройки.
4. Выберите рабочую папку (`Workspace`), иначе composer может быть недоступен.

Локальный адрес на самом сервере: `http://127.0.0.1:3080`.

### Перед запуском

Сценарий имеет несколько потенциально разрушительных действий:

- останавливает и отключает перечисленные выше сервисы;
- удаляет `/etc/systemd/system/dsh.service`, `caddy-proxy.service` и `caddy-https.service`;
- завершает процессы, слушающие выбранный порт;
- изменяет файлы глобально установленного пакета `dsh`.

Если на сервере уже используются dsh, Caddy или порт `3080`, заранее сохраните их конфигурацию и проверьте содержимое сценария.

## Настройки через переменные окружения

Переменные читаются при запуске сценария:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DSH_PORT` | `3080` | Порт веб-интерфейса и порт LAN-оверлея. Порт должен быть свободен. |
| `DSH_FORCE_REINSTALL` | `0` | При значении `1` повторно устанавливает `@deepseek-ai/dsh`. |
| `DSH_SKIP_PRIVILEGED_PATCH` | `0` | При значении `1` не патчит серверный API-шлюз. Settings/Models по LAN, как правило, будут возвращать `403`. |
| `DSH_SKIP_CLIENT_PATCH` | `0` | При значении `1` не патчит клиентский `isLoopback`. Для настройки используйте loopback-адрес. |
| `DEEPSEEK_API_KEY` | не задана | Если задана, добавляется в окружение systemd-сервиса `dsh`. |

Пример запуска на другом порту:

```bash
export DSH_PORT=8080
./dsh.sh
```

Если вы запускаете сам сценарий через `sudo`, используйте `sudo -E`, чтобы передать переменные окружения:

```bash
sudo -E ./dsh.sh
```

При повторном запуске существующий `~/.dsh/overlays/lan.yml` **не перезаписывается**. Если нужно изменить порт, проверьте и вручную обновите этот файл перед перезапуском.

### API-ключ

Если ключ нужно передать сервису сразу:

```bash
export DEEPSEEK_API_KEY='sk-...'
./dsh.sh
```

Если запускать сам файл через `sudo`, используйте `sudo -E`, иначе `sudo` может не передать переменную в сценарий. Учтите, что ключ записывается в `/etc/systemd/system/dsh.service` в открытом виде. Не передавайте его в командной строке на общей машине и ограничьте доступ к unit-файлу.

## Что изменяется на диске

| Путь | Назначение |
| --- | --- |
| `~/.dsh/overlays/lan.yml` | Конфигурация привязки веб-сервера к LAN. Создаётся только при отсутствии файла. |
| `~/dsh_fix_YYYYMMDD_HHMMSS.log` | Основной лог запуска. |
| `~/dsh.log` | Лог фонового запуска, если активный systemd не найден. |
| `/etc/systemd/system/dsh.service` | Unit-файл сервиса и его автозапуск. |
| `*.dshbak` | Резервные копии изменённых файлов `dsh-client-connection`. |
| `~/.ssh/known_hosts` | Добавленная запись для `github.com`. |

Фактический домашний каталог зависит от пользователя, определённого сценарием. При запуске через `sudo` из-под обычного пользователя сервис создаётся для исходного пользователя (`SUDO_USER`), а не для root.

## Управление сервисом

На системах с работающим systemd:

```bash
sudo systemctl status dsh
sudo systemctl restart dsh
sudo journalctl -u dsh -f
```

Проверка порта и веб-интерфейса:

```bash
ss -ltnp | grep ':3080'
curl -I http://127.0.0.1:3080/
```

Если systemd не активен, сценарий запускает `dsh` через `nohup`; автозапуск после перезагрузки в этом режиме не настраивается. Лог такого запуска находится в `~/dsh.log`.

## Firewall и безопасность

Firewall сценарий не меняет. Ограничьте порт только нужной подсетью, например для сети `192.168.0.0/16`:

```bash
sudo ufw allow from 192.168.0.0/16 to any port 3080 proto tcp
```

Адаптируйте подсеть и порт под свою сеть. Не используйте широкое правило вроде `allow 3080/tcp`, не настраивайте проброс порта на WAN и не считайте LAN-патчи заменой аутентификации или TLS. Перед применением серверного патча сценарий выводит предупреждение именно потому, что привилегированные операции становятся доступны доверенным LAN-хостам.

Дополнительно учитывайте:

- обновление или переустановка `@deepseek-ai/dsh` может затереть патчи; повторный запуск сценария попробует применить их снова;
- патч применяется только при совпадении ожидаемых строк конкретной версии пакета, поэтому после обновления он может не примениться;
- плагин и глобальный пакет устанавливаются из внешних источников и требуют сетевого доступа;
- скрипт добавляет результат `ssh-keyscan` в `known_hosts`; перед использованием в строгой модели безопасности проверьте отпечаток ключа GitHub самостоятельно.

## Диагностика

### `settings are unavailable in this browser`

1. Выполните жёсткое обновление страницы (`Ctrl+Shift+R`).
2. Открывайте интерфейс по `http://<LAN-IP>:<порт>`, а не по имени хоста, которое может разрешаться неоднозначно.
3. Проверьте лог запуска и убедитесь, что не были заданы `DSH_SKIP_PRIVILEGED_PATCH=1` или `DSH_SKIP_CLIENT_PATCH=1`.
4. Проверьте, что в серверном `index.js` появилась `trustedHosts`, а в клиентском `client.js` — `isLoopback: true,`.
5. После обновления `dsh` повторно запустите сценарий с `DSH_FORCE_REINSTALL=1`, если это необходимо.

### LAN возвращает `403`

Это означает, что серверный патч не применился или был отключён. Запустите сценарий без `DSH_SKIP_PRIVILEGED_PATCH=1` и проверьте сообщения о резервной копии и ожидаемой строке. Внешний Host намеренно должен оставаться заблокированным (`403`).

### Сервис не запускается

```bash
sudo systemctl status dsh
sudo journalctl -u dsh --no-pager -n 100
ss -ltnp | grep ':3080'
```

Также проверьте `~/.dsh/overlays/lan.yml`: при существующем файле сценарий не исправляет порт в нём автоматически.

### Плагин не установился

Посмотрите основной лог и попробуйте после исправления сетевой или npm-проблемы:

```bash
dsh plugin --profile web add dsh-web-lan-access
dsh plugin --profile web list
```

Если npm-источник недоступен, сценарий использует запасной источник `github:AcidGr/dsh-web-lan-access`.

## Повторный запуск и откат

Повторный запуск безопаснее выполнять после проверки текущих unit-файлов, порта и оверлея. Для принудительной переустановки dsh:

```bash
export DSH_FORCE_REINSTALL=1
./dsh.sh
```

У сценария нет отдельной команды `--uninstall`. Минимальная остановка systemd-сервиса:

```bash
sudo systemctl disable --now dsh
sudo rm -f /etc/systemd/system/dsh.service
sudo systemctl daemon-reload
```

Для отката патчей найдите созданные рядом с пакетами файлы `*.dshbak` и восстановите соответствующий оригинальный файл от имени root. Удаление глобальных пакетов, оверлея, логов и плагина выполняйте отдельно, только если они больше не нужны другим проектам.

## Проверка репозитория

Сценарий не содержит отдельного набора автоматических тестов. Базовая проверка синтаксиса выполняется без запуска установки:

```bash
bash -n dsh.sh
```

Полноценная проверка требует Linux-систему с `sudo`, Node.js/npm, доступом к сети и возможностью запустить `dsh`.
